## Why the `sdk` bump matters here specifically

**`candy/plugin-docs` imports `sdk/candywalk` at three sites — `catalog.go`, `sources.go`, `gen_skills.go` — and the corpus walk it drives is the phase that the docs deploy's "Regenerate the generated content from the pinned charly" step spends 20–35 minutes inside, printing nothing** (`opencharly/docs#162`).

**`sdk v0.2026289.800` adds one line per resolved ref:**

```
charly: resolving <repo>:<version> (N resolved, M queued)
```

> ***Emitted BEFORE each resolve, so the last line in the log names the ref currently being worked on.*** *The download half already reported per repo (`spec/refs`' `Downloading %s:%s...`); the resolution half — which dominates the runtime — reported nothing, and that is why characterising that step took a `SIGQUIT` goroutine dump rather than a log read.*

***So this bump is the producer step that carries the observability to the docs bed:*** `plugin-docs` adopts `sdk` → this tag → the docs deploy workflow's pinned `plugin-docs` advances → the step prints progress.
