# 2026.288.1716 — fix(docs): the candy-skill complement fails loudly, and the duplicate reader is gone

## Summary

Two changes to the docs generator, both about the same thing: **one reader, and no silence.**

**1. The candy-skill complement now fails loudly (`plugin-docs#18`).** `collectCandySkills` used to swallow a decode failure:

```go
if err := e.Value.Decode(&s); err != nil {
    continue          // ← the entity vanished from the projection with no signal at all
}
```

That is the complement that keeps a **moved** candy's recipe references resolving before the marketplace regeneration lands — and when it silently omitted a skill, every page still built and nothing anywhere said so. That silence is how a 215-file marketplace pin lag could hide behind it. It now returns `([]skill, error)` with the entity name and its source directory, and `generate.go` propagates it. The `Type == "agent"` skip beside it is deliberately untouched: that one is a decision, not a failure, and conflating the two would be its own defect.

**2. The duplicate reader is gone (F14/R2).** `readSkill` read `<skillsDir>/<name>/SKILL.md` by hand — including the generator's DO-NOT-EDIT marker strip — beside the SDK kit's `candywalk.ReadSkillFile`. `collectSkills` now calls the kit. The marker regex that only `readSkill` used went with it, and so did the two imports it orphaned (`regexp`, `yaml`) — the compiler found those, not me.

**Scope, stated because it looks like an omission:** `splitFrontmatter` **stays**. Its one remaining caller is `links_site.go`, asking a different question of a different input — whether an *emitted page* carries frontmatter at all. The kit exports no equivalent, and routing that through the corpus reader would fit worse than a small local splitter. R2 applies to the behaviour, not to the name.

**Two pins move, and the body now accounts for both.**

- `github.com/opencharly/sdk v0.2026266.2340 → v0.2026288.1246` — the kit reader this handover calls.
- `github.com/opencharly/spec v0.2026267.747 → v0.2026287.1529` — carried along because the SDK tag declares its own `spec` requirement and MVS settles there; it is not an independent bump and nothing in this change depends on it directly.

I checked the symbol resolves (`go doc … ReadSkillFile`) *before* writing code against it — the lesson the generator leg learned the hard way, where a green build proved nothing because nothing referenced the new symbol yet.
